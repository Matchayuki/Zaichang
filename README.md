## 一、为什么做「在场」 💬

### 🪞 显影的另一半

显影的核心命题是：**帮助难以开口的人，在 90 秒内整理并发出一条别人知道该如何回应的信息。**

这句话里藏着一个未经检验的前提——**接收者知道该怎么回应。**

现实往往相反。收到一段脆弱的倾诉，最常见的反应不是冷漠，而是**僵住**：

- 😶 想回，但不知道回什么，怕一句话把事情弄得更糟；
- 🫂 想帮，但怕接不住对方的情绪，也怕为自己接不住的东西负责；
- ❓ 想问「你还好吗」，又怕对方其实不想被追问；
- 🫥 最后退回最安全的选项：`嗯` `抱抱` `我在` —— 或者干脆沉下去，假装没看见。

倾诉者花了很大力气才说完的那句话，在接收者这一端落了空。**一整条链的勇气，断在最靠近人的那一环。**

显影站在**说出口的那个人**这边。「在场」站在**收到的那个人**这边。

两者**没有账号、数据或运行依赖**，是两个各自独立的入口，不是同一个产品的两个页面。这是刻意的设计选择：求助者的表达和接收者的回应，不应该共享一份数据，也不应该互相可见。

### 🎯 我们真正想解决的，不是「不会说话」

如果问题只是措辞，那一个模板库就够了。但真正让人僵住的是三件更难的事：

> **1️⃣ 分不清对方要什么。**
> 同一段话里可能混着「你别告诉我妈」「你陪我一会儿」「我只是想有人知道」——接收者往往读不出来，或者过度解读。
> → 在场只认**朋友明确说出口的请求**，不推测，不脑补。

> **2️⃣ 不确定自己能陪多少。**
> 很多人的犹豫不是不想陪，是怕接了就下不来。答应一次深夜长谈，意味着接下来两周都要随时在线。
> → 在场先把「能陪多少」做成一道**明码标价的题**：十分钟、今天下午、这周一次，都可以。没有选择就不进入下一步。

> **3️⃣ 怕一句关心变成终身责任。**
> → 在场把陪伴拆成**一次性的具体小事**（一起吃个饭、周六下午走一段），并且明确：状态来自你自己的记录，不是对方的授权凭据。

### 🤝 三个坚持

| | | |
|:--:|:--|:--|
| 🙅 | **不代笔，只起草** | 输出永远是草稿。你必须改成自己的语气再复制走——它替不了你做那个朋友。 |
| 📏 | **不越界，先量力** | 先问「你能陪多少」，再谈怎么陪。余力为零时不生成任何承诺。 |
| 🧹 | **不留存，不追踪** | 默认不保存。主动保存时，只留一份本机约定，不保存聊天原话，也不保存回复。 |

## 二、它怎么做 🧭

<div align="center">

**👂 听见 TA　→　🪞 看看自己　→　✍️ 回一句话**

</div>

| | 步骤 | 做什么 | 关键约束 |
|:--:|---|---|---|
| 1️⃣ | **听见 TA** | 看一段朋友的原话，或试一个明确标注为虚构的练习场景 | 只选择**朋友明确说过的**请求，不替 TA 补需求 |
| 2️⃣ | **看看自己** | 选择此刻能陪多少 | **没有选择时不会进入回应步骤** |
| 3️⃣ | **回一句话** | 拿到草稿，改成自己的语气，复制到聊天里 | 手改过的文字**不会被自动覆盖**；返回调整也保留 |

想继续陪伴时，从回应后的入口或顶部「留一点时间」，再约一件具体的小事。自己记录「TA 说好啦」之后，可以导出个人日历。

也可以完全没有 AI：不填任何东西，就当一份「收到消息时该问自己的问题清单」来用。

### 🔧 关键决策：每一处改动都对应一句具体的否定

| 收到的反馈 | 决策 | 为什么这么改 |
|---|---|---|
| 🗣️ 「美术太差，而且文本很生硬」 | 重做全部文案语感 | 生硬的关心比不关心更伤人，先把话写得像人话 |
| 🧱 「排版真的很差劲，完全推倒重来」 | 弃用平铺工作台 → 三步引导 | 低能量状态下，选择越多越走不动；一次只问一件事 |
| 🌇 「改成暖色系」 | 暖纸底 + 墨蓝文字 + 鼠尾草绿操作色 | 冷色调在情绪场景里像工具，不像陪伴 |
| 🖼️ 「插画数量有点少」 | 补齐场景插画，统一相框 | 空界面会让停留成本变高，插画提供可呼吸的留白 |
| 🔤 「字体太复杂太割裂了，最多两种」 | 收敛到一种正文字体，其余全部下线 | 字体即语气，混用会破坏可信度 |
| 🎭 「图二太真实太突兀了」 | 真实感插画改绘为油画 | 具象人物容易让用户对号入座，油画提供安全的距离感 |
| 🐛 「回字内部全黑」（字形 bug） | 修复字形渲染 | 视觉信任是一票否决的 |

### 🧵 一条贯穿始终的原则

> [!NOTE]
> **马尾原则**：每个方向只解决一个具体问题。
>
> 显影早期的教训是同时想做四件事——情绪记录、呼吸练习、表达生成、转介卡片，结果低能量用户一进来就被选择劝退。「在场」因此只保留一条主线：**收到 → 回应 → 陪一会儿**。其余功能（日历导出、留一点时间）都是这条线上的延伸，不是并列的第二个产品。

## 四、它不做什么 🚧

这些边界写在显眼处，不是免责声明，是产品本身的一部分。

- 🚫 **不是心理咨询、不是测谎、不做情绪识别。** 回应由 DeepSeek 根据原话、可选背景、朋友明确表达的需要和用户自己的余力生成，用户可编辑、核对后再复制。
- 🔇 **没有代发、聊天回执、好友关系、多人同步或自动提醒。** 状态来自用户自己的记录，不是对方的授权凭据。
- 💾 **默认不保存。** 主动保存时只保留一份本机约定（键名 `zaichang_plan_v1`），不保存聊天原话或回复，不访问显影的存储。
- ✍️ **手改过的草稿不会因选择变化被替换**，需要本人确认后才会重新整理；修改时间或安排会撤销之前的确认与完成状态。
- 📅 **日历采用 UTC 时间与转义文本**，不携带昵称、不发邀请、不添加自动提醒。日历服务仍可能同步你填写的安排细节，`CLASS:PRIVATE` 不等于加密。
- 🔑 **不使用外部字体、分析埋点或前端 API Key。** AI 能力由服务端通过环境变量接入，密钥不出服务器。
- 📦 **纯静态页面可以部署到 GitHub Pages**，但那样只能使用浏览与本机约定功能；要启用 AI，需要把 `server.cjs` 部署到支持 Node.js 的服务并设置密钥。

## 五、运行与部署 🚀

### 🏗️ 线上架构

```
浏览器 (GitHub Pages · 静态)
   │  https://matchayuki.github.io/Zaichang/
   │
   └─▶ https://zaichang.onrender.com/api/   ← Node 服务 (Render)
              │
              └─▶ DeepSeek /chat/completions（密钥仅在服务端）
```

前端不含任何密钥；AI 地址写在 `index.html` 的 `zaichang-api` meta 中，指向生产后端。

### 💻 本地开发

```bash
node test.cjs     # 核心逻辑与接口检查
node build.cjs    # 构建 + JavaScript 语法与 DOM 引用检查，产物在 dist/
```

直接打开 `index.html` 可以浏览界面，但 **AI 生成必须经过 `server.cjs`**，静态文件服务器无法替代。本地预览示例：

```bash
python -m http.server 4182 --bind 127.0.0.1
```

### 🔐 服务端环境变量

| | 变量 | 说明 |
|:--:|---|---|
| 🔑 | `AI_API_KEY` | DeepSeek 密钥，**仅服务端**，不要写进前端或提交到仓库 |
| 🌐 | `AI_BASE_URL` | `https://api.deepseek.com` |
| 🧠 | `AI_MODEL` | `deepseek-v4-pro` |
| 🖥️ | `HOST` | `0.0.0.0` |
| 🛡️ | `APP_ORIGIN` | `https://matchayuki.github.io`（来源校验白名单） |

### 📂 文件分工

| | 文件 | 职责 |
|:--:|---|---|
| ⚙️ | `core.js` | 输入约束、约定状态、存档校验、日历生成 |
| 🖱️ | `app.js` | 界面交互、三步引导、AI 生成、手稿保护 |
| 🤖 | `ai.cjs` | DeepSeek OpenAI 兼容接口与 JSON 结果校验 |
| 🛡️ | `server.cjs` | 静态资源白名单、来源校验、请求大小与频率限制、超时与错误处理 |
| 📦 | `build.cjs` | 构建与自检（未引入新依赖） |

`dist/` 为构建产物，包含页面所需的静态资源与自托管字体，可独立移动。
